### What to investigate, in order

  `smallest_fraction`; where display formatting and stored value diverge
- dirty state, `refresh_field`, `set_value`, `toggle_display`, and the re-render cost model

**Doc `docs/ui/02-child-table-grid-engine.md`**

**Doc `docs/ui/05-our-frontend-and-form-spec.md`** — the deliverable
The equivalent of `docs/logic/25-our-platform-spec.md` for the presentation layer:
- **layout as data, versioned**: an approved, immutable form-layout revision per doctype/role/company
  with an effective range — not a mutable pile of Property Setters
- a typed layout tree (tab → section → column → field) validated at publish time, so a malformed layout
  cannot be saved; no reliance on ordered break rows
- a constrained, declarative visibility/mandatory expression language with a validated AST and a version
  hash, evaluated identically on client and server. **Never** `eval` of user text.
- field-level permission and visibility resolution stated once, server-authoritative, with the client as
  a cache
- grid contract: server-driven column sets, stable row identity independent of `idx`, explicit residual
  rules for computed columns, and a stated row-count budget with virtualised rendering above it
- formatting contract: display formatting is a pure function of value + locale + field precision;
  **stored values are never formatted or translated** (this is invariant U7 in the backend work — keep it)
- customisation contract: layout revisions and expression revisions are migratable artefacts in version
  control, with a diffable export, and an explicit story for upgrade conflicts
- accessibility and keyboard-first data entry as stated requirements, with the grid as the primary case
- an explicit **build / buy / drop** decision per capability, matching doc 25 §6's format

### Answered product constraints you must design for

- **India GST is a required localisation.** Forms must handle HSN/SAC, place of supply, GSTIN, reverse
  charge, and CGST/SGST/IGST/cess breakdown display. Localised field sets and labels are therefore a
  **first-class layout concern**, not a regional patch — the backend agent is explicitly rejecting
  ERPNext's `@allow_regional` override mechanism, so do not design around it.
- Multiple tax regimes are in scope, so layout must vary by jurisdiction without forking the doctype.
- Stored codes are never display text; every label is rendered at read time.

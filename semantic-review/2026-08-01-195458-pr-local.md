# Production, ownership, and quality schema closure

The change closes Tranche B by mapping M1–M69 onto a production schema layered over the existing stock and accounting ledgers. It adds owner/custodian dimensions, versioned definitions, planning and execution records, conversion costing, subcontract custody, quality evidence, idempotency, and outbox/projector infrastructure. Several claimed invariants cannot be enforced by the tables and ordering as written, especially where immutable facts depend on mutable valuation projections and where quality completeness is represented one criterion or command receipt at a time. Citation verification succeeds at the stated 4,598 total, and no stale completion claim or malformed local link was confirmed.

Watch for: **confirmed** immutable conversion costs cannot remain exact when `stock_valuation_state` is recomputed after backdating; **confirmed** the posting order requires production rows to be updated after insertion; **confirmed** quality criteria and release consumption do not establish complete, bounded release; **confirmed** the raw `app.company_id` GUC does not authenticate tenant context; **confirmed** several M-invariants name constraints or durable records absent from the schema.

**Verdict**: NEEDS_CHANGES

## High-level view

The model reuses `stock_move`, `voucher`, and `gl_entry`, but treats valuation output both as a rebuildable projection and as immutable input to conversion and accounting facts. Backdated recomputation can change an old move’s value without an append-only GL correction, so M35/M37/M43/M50 cannot remain continuously true.

Conversion rows are inserted before the stock moves and valuation results that supply their move IDs and amounts, despite being described as immutable evidence. Reversal ordering also differs between the conversion and quality sections.

Owner/custodian dimensions reach stock, planning, reservations, and production, but owner policy is mutable, party kind is not proved, and title transfer lacks explicit before/after dimensions for a direct conservation constraint. Versioned definitions likewise omit effective-range enforcement for calendars and several other revisions, while capacity and downtime lack one enforceable shared model.

Quality has the right conceptual layers, but mode-specific criterion validity, exact sample positions, one current release, quantity-bounded consumption, multi-criterion gate completeness, and much of the promised QM snapshot model are absent. M56–M69 are therefore only partially enforced.

Command receipts and event/outbox rows have useful identities, but concurrent retry behavior, durable terminal failure, child-row cardinality, and event-to-outbox coupling are incomplete. RLS is broad, yet its tenant identity is a caller-set custom GUC rather than a non-spoofable authenticated binding.

## Rebuildable valuation cannot be an immutable costing authority

**Confirmed.** `FINAL-SCHEMA.md` §4 defines `stock_move` as the event and `stock_valuation_state` as a recomputable projection. Sections 14, 17, and 18 require production input `realised_value`, output `stock_value`, and immutable `gl_entry` amounts to equal that projection continuously for M35/M37/M43/M50. A backdated move can change a later projection row’s `value_delta`; the corresponding production rows and GL entries cannot change. No adjusting valuation event/voucher or closed valuation watermark is defined, and `stock_move` has no immutable value delta. Its pre-existing zero-quantity revaluation rule is not representable from `qty_delta` and `unit_rate` alone.

Choose one authority. Either freeze posted valuation and append zero-quantity value-adjustment moves plus linked vouchers, or append a valuation-adjustment event/voucher for every replayed historical delta and define the bridge over original plus adjustments. If closed history cannot move, enforce a valuation/period watermark. Add an immutable signed value amount or typed value-adjustment payload to `stock_move`.

**Confirmed.** The §14 equation omits `production_loss.amount`, although that table carries an amount and value policy. M33/M35 need an explicit rule: normal loss is absorbed into surviving outputs, abnormal loss is a named expense/variance leg, and valued scrap is counted as an output exactly once.

## Conversion rows cannot be populated in the stated append-only order

**Confirmed.** `FINAL-SCHEMA.md` §14 gives `production_input` a `realised_value`, `production_output` a `stock_value` and `stock_move_id`, and `production_conversion` a `voucher_id`. The prose inserts conversion rows, then stock moves and valuation, then “assigns” `stock_move_id`, and only later inserts the voucher. `FINAL-SCHEMA.md` §17 and doc 40 §6.4 repeat that order. Those values do not exist at initial insertion, so the protocol leaves authoritative columns null or updates posting evidence afterward.

Insert immutable conversion authorisation first, then stock moves/valuation, then immutable valuation allocations and voucher links with all values known. Alternatively let stock moves reference stable conversion-line identities and place later associations in append-only link facts. Associations required by costing and reversal are evidence, not disposable projections.

## Reversal order disagrees across production and quality

**Confirmed.** Doc 40 §6.4 inserts reversing stock moves and GL before reversing gate/allocation facts. Doc 40 §6.6 and `FINAL-SCHEMA.md` §17 reverse gate consumption first. Posting summaries also differ on whether idempotency precedes company/period guards and omit the account-owner lock from §17 despite doc 40 §5.1 making it the final lock class.

Publish one state machine and reference it from both files. Reverse gate consumption first with a deferred dependency check permitting the dependent reversal in the same transaction, then reverse stock and GL; or define another single atomic deferred order. Claim idempotency before side effects and specify replay of rejected commands.

## Owner identity does not prove ownership semantics

**Confirmed.** `FINAL-SCHEMA.md` §4 checks only owner-field nullability. A `customer` owner can point to a supplier party, a custodian kind can disagree with its party, and mutable `valuation_policy` can retroactively reclassify referenced stock streams. Section 15’s `custody_transfer` points to two moves but does not expose source/target owner and custodian, leaving owner preservation/title transfer as prose.

Use typed owner subtypes or a trigger proving party kind and company. Freeze owner policy once referenced, or version and snapshot it on moves/conversions. Store from/to owner and custodian plus authority on title/custody transfer, with deferred quantity, tracked-unit, ownership, value, and GL constraints over the paired moves.

## Mutable current-state markers contradict additive correction

**Confirmed.** The convention derives current state from reversal/supersession chains, but §13 defines `execution_lot_serial.is_current`. Doc 40 §6.3 says to “mark WO reversed” while also making posted production additive; capacity, planning, and quality rows combine reversal links with mutable states without classifying those states as facts or projections.

Derive open serial allocations from unreversed edges. Represent released/reversed/closed transitions as append-only lifecycle events and keep mutable state only in named projection tables. If headers retain draft state, define and enforce the release freeze point.

## Effective revisions and capacity do not enforce M7–M12

**Confirmed.** `FINAL-SCHEMA.md` §11 gives overlap exclusions to policy, BOM-default, and quality-template revisions, but not `operation_revision`, `route_revision`, `resource_rate_revision`, or `resource_calendar_revision`; several also lack interval checks. M9’s one-effective-calendar claim therefore permits two approved calendars for the same resource/date.

Add approved-range exclusions and interval checks to calendars/rates and any route/operation resolved by date. If explicit revision selection intentionally allows overlap, state that and narrow the one-effective-version rule.

**Confirmed.** Section 13’s capacity-one exclusion depends on parent `resource.capacity_units`, while parallel capacity uses a separate summed rule and `downtime_event` does not reference the same day-owner/constraint surface. Materialize capacity slots or use one deferred trigger that locks all affected resource-days and sums reservations plus downtime against a snapshotted capacity/calendar revision.

## Quality definitions and samples are structurally incomplete

**Confirmed.** `FINAL-SCHEMA.md` §16 only limits simultaneous `expected_value` and `expression_ast`. It permits numeric criteria without bounds, value criteria without expected values, formula criteria without expressions/hashes, and mode-incompatible fields. Observation position is positive but not bounded by the required count, and no relational rule proves an observation criterion matches its attempt’s requirement.

Add mode-specific field checks, canonical-UOM rules, validated formula hash/version, exact positions `1..required_observations`, and attempt/requirement/criterion/unit/sample agreement. Enumerate these refusal conditions for the deferred trigger.

## Quality release is not unique-current, bounded, or complete

**Confirmed.** Section 16 permits multiple original releases for one requirement because uniqueness covers only command and reversal IDs. Gate consumption has no consumed quantity, so repeated consumers can exceed `released_qty`; per-consumer uniqueness does not prove every criterion attached to a quality owner passed before stock/operation posting.

Enforce one current disposition/release per requirement revision under the quality-owner lock. Add `consumed_qty` and `SUM(unreversed consumed_qty) <= released_qty`, then define either one gate row per criterion or an aggregate release created only after the frozen criterion set passes. Add a deferred completeness check from consumer to that full set.

**Confirmed.** `quality_gate_consumption` also has `UNIQUE (company_id, command_receipt_id)`, so one command cannot emit gates for multiple criteria or stock lines. Include a child ordinal/scope hash or use an idempotent command-result header with child rows.

## The QM schema does not cover M57/M64

**Confirmed.** Doc 39’s target model and doc 40’s M57/M64 require versioned feedback questions/responses, goal objectives, review results, non-conformance, action/task closure, and meeting evidence. `FINAL-SCHEMA.md` §16 includes only goal revision, review occurrence, procedure revision/edges, and a generic action event.

Narrow closure to operational quality and leave QM workflow open, or add doc 39 §12.3’s missing revision/evidence tables with typed sources and lifecycle events. M64 should name concrete FKs from review/feedback/action evidence to immutable source revisions.

## Idempotency and event/outbox coupling are incomplete

**Confirmed.** `command_receipt` promises replayed results and terminal errors but does not define concurrent in-progress behavior. A receipt in the business transaction loses its terminal error on rollback; a separately committed receipt needs lease/takeover and commit-discovery rules. Unique command receipts on plural children such as `execution_lot` also prevent one WO-release command from creating multiple rows.

Define insert-or-select, in-progress wait/takeover, hash validation, success publication, and failure retention. Use one receipt per external command and child identities `(command_receipt_id, ordinal/scope)`.

**Confirmed.** `production_event` and `transactional_outbox` repeat aggregate/type/position independently without an event FK or one-to-one constraint. Missing, orphaned, or mismatched rows satisfy the current keys; a committed position gap can stall contiguous projectors. Give outbox an `event_id UNIQUE` FK and derive duplicated fields, then allocate positions under an aggregate owner lock.

## The RLS policy trusts a spoofable tenant setting

**Confirmed.** The policy at the top of `FINAL-SCHEMA.md` compares `company_id` with `current_setting('app.company_id', true)::bigint`. PostgreSQL custom settings can be changed by an ordinary session; `FORCE RLS` prevents owner bypass but does not authenticate the selected value. A shared application role can select another company and satisfy `USING` and `WITH CHECK`.

Use a tenant-context function that validates principal/company membership from state the application role cannot forge. Options include principal-specific database roles or signed context set through a narrowly granted `SECURITY DEFINER` entry point. Keep context transaction-local and test attempted forgery.

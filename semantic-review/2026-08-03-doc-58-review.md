## Blocking

### B1 — `format_revision_id` references a table that does not exist

`statutory_series.format_revision_id NOT NULL` is annotated `-- the jurisdiction's format rule (§24)`
(doc 58:356). **`FINAL-SCHEMA` §24 has no document-number format revision table.** It has
`tax_jurisdiction_revision`, `classification_code_revision` and `tax_rate_revision`. The only table in the
whole file whose name ends `format_revision` is `return_format_revision` (§27, line 2607), which versions
the *file layout of a statutory return* — GSTR-1's JSON shape — and has nothing to do with the format of a
document number.

The column is therefore a dangling reference, and it is load-bearing: it is the entire reason §8 can claim
"the design is jurisdiction-agnostic". Nothing can be transcribed until the referent exists.

### B2 — `statutory_year_id` references a table that does not exist

`statutory_series.statutory_year_id NOT NULL`, annotated `-- the STATUTORY year, not the fiscal calendar`
(doc 58:353). **There is no statutory-year table anywhere in `FINAL-SCHEMA`.** The nearest thing is
`return_period` (§27), which is the statutory *return* period — a month or a quarter — not a year, and not
usable as a series key.

The distinction the annotation draws is real and correct: India's GST year runs 1 April – 31 March
regardless of a company's chosen fiscal calendar, and G31 depends on the series being keyed on the statutory
year. But the table that would hold it was never written.

## Design defects

### D1 — the `CHECK` hard-codes India into a jurisdiction-agnostic table

```sql
CHECK (statutory_number ~ '^[^\W_][A-Za-z0-9\-/]{0,15}$')
```

This is Rule 46(b), an Indian rule, compiled into a table constraint — on the same table that carries
`format_revision_id` precisely so that the format can be data.

That is `@allow_regional` in schema form. `FINAL-SCHEMA` §24 opens by rejecting exactly this mechanism
("We reject that mechanism and ERPNext's `@allow_regional` function replacement … in favour of jurisdiction
as data"), and G1/G2 make it an invariant. Under this `CHECK`, adding UAE means an `ALTER TABLE` — a code
path selected by jurisdiction, which is the thing the tranche exists to prevent.

The format belongs on the format revision (B1's table) as a pattern plus a maximum length, enforced by an
L2 trigger that reads the revision the series points at.

### D2 — `UNIQUE (company_id, statutory_number)` contradicts G31 and forbids a lawful state

G31 states, and §5.1's own comment argues at length, that statutory uniqueness is **per registration and
per statutory year** — "a company with two GSTINs runs two independent series". The series-level `UNIQUE`
encodes that correctly.

The allocation-level constraint then throws it away: `UNIQUE (company_id, statutory_number)` is
company-wide. A company registered in two states cannot issue `INV/001` from both, which is lawful, and
which is the precise case G31 was written for. The constraint should be
`UNIQUE (company_id, statutory_series_id, statutory_number)` — the series already pins registration, class
and year.

### D3 — a series can be declared that is incapable of producing a lawful number

`prefix varchar(8)`, `width` up to 12 (`CHECK (width BETWEEN 1 AND 12)`), `suffix varchar(8)`. That composes
up to **28 characters** against a 16-character statutory ceiling. Nothing constrains the declaration.

The refusal then lands at *allocation* time — possibly months into a year, on a series already in use, at
the moment a user is trying to issue an invoice. G34's own reasoning ("refuse at issue, not at filing"),
applied one level up, says refuse at **declaration**. The series needs
`CHECK (length(prefix) + width + length(suffix) <= <max from the format revision>)`, which is a second
reason B1's table has to exist rather than a literal 16.

### D4 — the "void allocation" the prose promises is not what the schema produces

§5.1: *"A rolled-back document leaves a `void` allocation, not a silent gap."*

With `next_value` on the series row, the allocation is drawn and the counter bumped inside the document's
own transaction. A rollback removes **both** — there is no gap and no `void` row, so the state the prose
describes never occurs. To produce a surviving `void` allocation the draw must commit independently of the
document (its own transaction, or a Postgres `SEQUENCE`, which does not roll back and therefore produces
the gap the `void` row exists to explain).

This matters because G32 makes the return a projection over allocations, and Table 13 must report
cancelled and void counts. As written, the schema cannot distinguish "never drawn" from "drawn and
abandoned" — which is the one thing the design claims over upstream's heuristic.

### D5 — `included_component_ids bigint[]` cannot carry referential integrity

An array of foreign keys is not a foreign key. The clean reference schema carries **2,051** FKs and reports
**0 dangling targets** precisely because a dangling reference is refused; this column reintroduces exactly
that, inside a rule that decides a statutory tax base. Superseding or deleting a `tax_component` leaves a
silent stale id.

It should be a junction table — `withholding_section_component(company_id, withholding_section_revision_id,
tax_component_id)` — which also makes G38's deferred constraint ("the included amount equals the sum of the
named components exactly") expressible as a join rather than `= ANY(array)`, and turns the `array_length`
`CHECK` into an ordinary count check.

### D6 — `withholding_regime` is a fourth global table, added to a list §24 declares closed

`withholding_regime` carries no `company_id`. `FINAL-SCHEMA` §24 states the exception explicitly and
exhaustively:

> **One deliberate exception to the company-scoping convention.** `tax_jurisdiction`, `tax_area` and
> `tax_area_postal_range` are **global reference data** … This is stated explicitly because doc 49 §2
> asserts company scoping for all localisation tables; these three are the exception.

Doc 58 adds a fourth without amending that paragraph. It is also a **build-gate failure**: §31's generated
`rls_conformance` view enumerates tables and requires `company_id` plus a policy, and it is step 6 of the
build order in doc 57 §8. An unscoped table fails it.

### D7 — `withholding_regime` has no jurisdiction

`statute` is an enum of `income_tax|gst|other` — Indian statute names — and `return_form` holds `24Q` and
`GSTR-7`. A withholding regime is inherently jurisdictional, yet there is no `tax_jurisdiction_id`. UAE has
nowhere to hang its regimes, which contradicts G1/G2 and §8's claim that only the *numbering* rules are
India-only.

## Statutory assertions — the weakest link, as `HANDOFF.md` §7 predicted

`HANDOFF.md` §7 asked specifically whether the statutory claims are stated as *upstream-observable facts*
or as *legal assertions*. The answer differs by claim, and one of them is load-bearing.

- **Rule 46(b)** (§2) is stated as law and then **evidenced** by `GST_INVOICE_NUMBER_FORMAT`, which encodes
  it exactly. Sound: the reader can check that upstream believes it too.
- **CBDT Circular 23/2017** and **s.206C(1H)** (§4.1) are stated as bare legal assertions with **no
  citation of any kind** — not a statutory reference, not an upstream one. And the entire G36 argument
  rests on them: "these two regimes disagree about the base, therefore the base cannot be a dropdown".

The design conclusion survives even if the two examples are imperfect — a base rule that cannot be dated
and attributed is wrong regardless. But the **specific bases must not be written into seed data on this
document's authority.** Golden rule 9: never guess an ERP business rule into a seed row. `authority` is
`NOT NULL` on `withholding_section_revision` for exactly this reason; the first rows to populate it need a
tax professional's sign-off, not a design document's.

**Recorded, not deferred:** doc 58 §8's three "not closed" items (GST TDS/TCS s.51/s.52, section
catalogues, non-India numbering) are honest scope boundaries and are correctly stated as such. No finding.

## What is right, and should not be re-argued

The review found no fault with the analysis half of the document. Recording it so a later session does not
redo it:

- **§2.1** — that the statutory number is `doc.name` and therefore the row's primary key is correct and
  fully evidenced (`frappe/model/naming.py:180-200`, `india_compliance/gst_india/utils/__init__.py:1030-1034`).
- **§2.2** — severity really does depend on document class, not on lawfulness: `frappe.throw` for Sales
  Invoice, `frappe.msgprint` for everything else, in one function. Verified.
- **§2.3** — `_set_amended_name` really does build the amended number by string concatenation and split on
  the last hyphen, and really is skipped when `amend_naming_rule == "Default Naming"`. Verified at
  `naming.py:576-586`.
- **§2.5** — the composition is real: a non-compliant number warns at save and is routed to
  `Excluded from Report (Invalid Invoice Number)` at filing (`gstr_1_data.py:947-949`). This is the
  strongest finding in the document and it holds.
- **§4.2** — `_item_total_tax_amount` really does sum every tax row that is not a withholding account, so
  freight and duty enter a "gross" withholding base. Verified at `tax_withholding_entry.py:552-566`.
- **§4.3** — the ordering claim is correct: GST is determined in `before_validate`, withholding runs in
  `validate`. Verified.
- **§7's Adopt/Change/Reject table** is complete and each row matches the body.
